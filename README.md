# rag-hybrid: hybrid search RAG over the Kubernetes docs, with an evaluation harness

A RAG service over 502 Kubernetes documentation pages (477 with body text): Elasticsearch BM25 and kNN, fused with a reciprocal-rank-fusion function I wrote, answers with validated citations, and a claim-level citation verifier. The repo is as much an evaluation harness for comparing retrieval modes as it is a service. Every figure below is generated by [`scripts/make_readme_tables.py`](scripts/make_readme_tables.py) from files in [`eval/results/`](eval/results/); the sources are listed in [`docs/NUMBERS_AUDIT.md`](docs/NUMBERS_AUDIT.md).

> **Caveats.** Only 26 answerable questions and no held-out set: every result is on one frozen golden set, so most differences between modes are within the noise.
> The citation verifier has not been validated against human judgement, so the faithfulness figures are verifier outputs, not measured accuracy.

## Architecture
- One Elasticsearch 9.5.5 index (`rag-docs`) holding both chunkers' output, separated by a `chunker` field: **fixed** (4,072 chunks, 400-token target) and **heading-aware** (4,527 chunks). `embedding` is a 1536-d `dense_vector` (`text-embedding-3-small`); effective `index_options` is `bbq_hnsw`.
- Three retrieval modes per request: **BM25** (`title^2`, `heading_path^1.5`, `content`), **dense** kNN, **hybrid** = Python RRF (k=60) over the two 200-chunk windows, then dedupe to documents.
- `/ask`: top 8 chunks (max 2 per page) to `claude-sonnet-5-5`, structured sentences with citations, validated in code; if the context lacks the answer it must refuse. `claude-haiku-5-5` then judges each (sentence, citation) pair against the cited text (rubric `claims-v2`: it lists claims, and the verdict is derived in code).
- FastAPI (`/search`, `/ask`), spend ledger with a hard limit, Docker Compose (ES, API, Kibana behind a profile).

| fixed/dense | 1.000 / 0.854 | 1.000 / 0.838 | 0.650 / 0.347 | 0.656 / 0.331 | conceptual |
| fixed/hybrid | 1.000 / 0.938 | 1.000 / 0.854 | 0.450 / 0.129 | 0.938 / 0.487 | conceptual |

| heading/hybrid | 1.000 / 0.875 | 1.000 / 0.906 | 0.550 / 0.240 | 1.000 / 0.610 | conceptual |

- **BM25 fails on paraphrased symptoms.** Conceptual questions deliberately avoid the page's vocabulary: BM25 Recall@10 is 0.000 (fixed) and 0.250 (heading).
- **Dense fails on pasted identifiers.** With only the exact term as the query (`bare_term`), dense falls to 0.656 / 0.719; BM25 and hybrid hold 0.938 / 1.000. With the full question around the term, dense is at ceiling on exact_term and mixed.
- **Hybrid does not win overall, and its worst slice is not the best worst slice.** Hybrid's worst slice (conceptual, 0.450 / 0.550) is far above BM25's but **below dense's** (0.650 / 0.683). Overall Recall@10, heading chunker: dense 0.878, hybrid 0.827 (n = 26, intervals overlap). Paired per question, hybrid vs dense (heading): 7 better, 12 equal, 7 worse; on conceptual questions 2 / 1 / 7 (better / equal / worse). The case for hybrid on this set is that it keeps the identifier-only queries that dense loses, at a cost on paraphrased ones; it is not a claim that hybrid beats dense.

## Answer evaluation
Pre-registered configs, 30 questions, context top 8 chunks / max 2 per page. The verifier judges each (sentence, citation) pair. **Strict faithfulness** = share of sentences with at least one cited excerpt judged `yes`; **lenient** = at least one judged `yes` or `partial`; **citation precision** = share of cited pairs judged `yes`. All three measure support by the cited excerpts, **not correctness**.

| config | answerable answered | false refusals | correct refusals (unanswerable) | answered when it should refuse | strict faithfulness (95% CI) | lenient | citation precision (95% CI) |
|---|---|---|---|---|---|---|---|
| heading/hybrid | 21 of 26 (0.808; CI 0.654-0.962) | 5 | 4 of 4 | 0 | 0.962 (0.924-1.000; 78 sentences, 21 answers) | 1.000 | 0.917 (0.864-0.974; 84 citations) |
| heading/dense | 23 of 26 (0.885; CI 0.731-1.000) | 3 | 4 of 4 | 0 | 0.961 (0.912-1.000; 77 sentences, 23 answers) | 1.000 | 0.951 (0.887-1.000; 81 citations) |

- Answered-or-refused is a retrieval story: context contained an expected page for 21 of 26 (hybrid) and 22 of 26 (dense) answerable questions, and most false refusals (5 hybrid, 3 dense) follow a retrieval miss. Coverage should be read next to faithfulness: a system that refuses more can look more faithful.
- Paired, answerable questions: both answered 20, only hybrid 1, only dense 3, both refused 2. Where both were verified, hybrid's strict faithfulness was higher on 2, equal on 16, lower on 2. No winner.
- **Refusals, n = 4:** both configs refused all 4 of 4 unanswerable questions (answered-when-unanswerable: 0). Two ask for the default of a kube-controller-manager and a kube-proxy flag whose names appear in no indexed chunk; for both, the retrieved context contained the related component configuration pages ([`answer_eval_review.md`](eval/results/answer_eval_review.md)), so they test a refusal next to topical pages. The other two are off-topic (sourdough, Jupiter). Not tested: unanswerable questions whose neighbouring page states a similar but different value, paraphrased unanswerable questions, or enough of them to estimate a rate (with n = 4 the exact 95% lower bound on the refusal rate is 0.40).

## Design decisions and what I would change
- **Python RRF is the default** because the native `rrf` retriever is Enterprise-gated (403 on a Basic licence). A cross-check on a 30-day trial (expires 2026-11-22) compared the two on 26 questions x 2 chunkers: first expected-page rank identical in 52 of 52; top-10 chunk order identical in 48 of 52. The differences are exact RRF score ties that Elasticsearch orders differently (float32 scores vs my exact fractions), see [`native_rrf_check.md`](eval/results/native_rrf_check.md).
- **Chunking:** fixed vs heading-aware is within noise on this set (hybrid Recall@10 0.788 vs 0.827, dense 0.865 vs 0.878; n = 26). Medians are 367 and 245 tokens; the heading chunker's maximum is 649.
- **Corpus cleaning:** the "What's next" sections (281 sections, 30,606 tokens) are stripped because they are navigation links to other pages, not answer content; 9 headless include partials are excluded because they are not public pages; 1,281 HTML entities are decoded outside code blocks.
- **Verifier:** claims-based. The model only lists claims and whether the cited text states each; the verdict is computed in code. The first rubric asked for the verdict directly and its `partial` became a loose bucket (faithful paraphrases marked partial).
- **Would change:** a held-out question set, a larger golden set, near-miss unanswerable questions, a cross-encoder reranker, and a human-validated verifier.

## Cost
Measured in the answer evaluation (claude-sonnet-5-5 + claude-haiku-5-5, both configs): 44 answered questions cost $0.0076 to $0.0190 each (median $0.0131); 16 refusals cost $0.0057 to $0.0136. The whole run was $0.7295 reported ($0.7296 summed from the logs). Live `/ask` costs vary with answer length: one answerable call was $0.0173 (worst-case estimate $0.053) and one refusal $0.0103. Retrieval evaluation makes no LLM calls. **Whole-project spend: about $1.1** (the spend ledger shows 1.0776 because the $0.0534 clean-clone embedding ran from the host).

## Limitations
- The verifier was not validated against human judgement: hand labelling was attempted three times and each attempt failed its own control checks, so no human-labelled accuracy is reported.
- Answers were compared with the reference answers by an automated judge only, and nobody has reviewed its output by hand, so that check is unvalidated and no correctness figures are reported. The judge flagged the answers to m007 and c007 as contradicting their references; those references may be too narrow.
- Also: the verifier mutation set is a dev set built from the verifier's own earlier failures; faithfulness numbers are verifier outputs; n is small (26 answerable questions); no held-out set, so all sensitivity runs are sensitivity analyses, not tuning.
- Three human labelling rounds of the verifier were attempted; round 1 had no controls and was inconsistent, rounds 2 and 3 failed their own pre-registered control checks. No human-labelled verifier accuracy is claimed anywhere. On the 25-pair mutation dev set the verifier caught 10 of 10 wrong pairs and gave `yes` to 5 of 5 verbatim and 10 of 10 paraphrased controls, but that set was built from the verifier's own earlier failures and the rubric was written after seeing them, so those scores are optimistic by construction.
- Only 26 answerable questions, one corpus, one snapshot (502 pages), so most differences have overlapping intervals.
- **Golden set provenance:** questions were drafted with LLM help from verified corpus excerpts, reworded against lexical overlap rules, the expected pages were checked against page text (not retrieval output) and approved by me, and the set was frozen before any evaluation. Conceptual questions deliberately avoid page vocabulary (median word-overlap ratio 0.635 vs 0.865 for exact_term; 0.6 shared rare terms on average, 0 copied phrases), which is the hardest case for BM25 and favours dense; overlap is a lexical proxy, not a guarantee.
- **Reproducibility is at document level.** Elasticsearch breaks equal-score ties by internal document id (indexing order), so chunk order among exact ties can differ between builds. A clean-clone rebuild reproduced BM25 rows exactly and moved 1 of 104 dense/hybrid first ranks ([`clean_clone_check.md`](eval/results/clean_clone_check.md)).
- **Outbound network:** Docker Compose cannot allowlist egress hosts, so the API container has default outbound access (it needs only ES and the two provider APIs). Mitigations: non-root, read-only filesystem, capabilities dropped, no secrets in the image, spend ledger, loopback-only ports.
- **Two spend ledgers exist** (Docker volume `rag-hybrid_apidata` and host `data/api/spend_ledger.json`); Docker is the supported mode. The limit is per ledger, not global.
