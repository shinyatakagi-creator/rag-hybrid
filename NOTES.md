## Phase 1
- **Corpus scope B** (511 pages) instead of the guide's "about 500 pages incl. all reference": excluded `reference/{kubernetes-api,glossary,command-line-tools-reference,setup-tools,kubectl}`. See `data/CORPUS.md` (SHA `6c42e266...`).
- **`--corpus-dir data/k8s`** is a symlink to `data/k8s-src/content/en` so `docs/`, `examples/` and `includes/` are all reachable. Only `docs/{concepts,tasks,reference}` become documents; `examples/` and `includes/` are read only to resolve `code_sample` / `include`.
- **doc_id** = path under `docs/` without `.md`, so `_index` pages are `.../_index` (their URL is the directory). No `docs/` prefix.
- **Shortcodes**: `include` inlined (except boilerplate `task-tutorial-prereqs.md`, 121 uses, stripped so identical text does not skew BM25), `code_sample` inlined as fenced blocks (7 references use a leading `/`; handled), `glossary_tooltip` -> its text, `glossary_definition` -> inlined short/full definition from the (checked-out but not indexed) glossary pages, notes/cautions -> "Note:" etc., `skew`/`param`/`version-check`/`thirdparty-content` stripped (build-time computed values are lost). Unknown shortcodes (`api-reference`, `example`, `link`, `page-api-reference`, `cve-feed`, `pageinfo`, `legacy-repos-deprecation`) are stripped and counted in the run output.
- **Hugo closing tags** are sometimes `{{</ name >}}` (space after the slash); the cleaner accepts both.
- **Layout HTML** (`td`, `tr`, `span`, ...) is stripped outside code fences, text kept.
- **Heading prefix**: the guide says both "prefix each chunk with its heading path" (Phase 1) and "embed heading_path + newline + content" (Phase 2). `content` is stored without the prefix and the prefix is added only when embedding, so it is not duplicated. `token_count` and the 800-token limit are measured on the embedded text.
- **Fixed chunker** gets only the page title as `heading_path` (structure-blind by design); it still obeys 800 tokens. **Yes, its embedded text also gets a prefix**: `embed_text()` is `heading_path + "\n" + content` for both chunkers, so a fixed chunk is embedded as `<page title>\n<content>`. The heading chunker gets the full path (`Title > H2 > H3`). So the chunker comparison differs in chunk boundaries and heading depth, not in whether a prefix exists; the fixed baseline is not prefix-free. BM25 `title` / `heading_path` fields are likewise populated for both.
- **Tiny-section merge** (<100 tokens) only happens inside one parent heading: into a descendant (intro -> first H2, empty H2 -> first H3) or between H3 siblings under the same H2; a tiny leftover folds back into its parent/sibling if the result stays <=600 tokens. It never crosses an H2/H1 boundary, so a tiny H2 stays a small chunk. Effect: more small chunks than a boundary-blind merge. The first draft merged across boundaries (605 forward + 210 backward crossings measured); that was a bug.
- **Oversize** tables and code fences are split at line boundaries; table header (and separator) and fence markers repeat in each piece; prose uses `RecursiveCharacterTextSplitter` (600 target, 50 overlap). 800 tokens is enforced after the prefix; the run aborts if any chunk exceeds it.
- **Hugo `## {{% heading "x" %}}`** already contains the hashes; first draft doubled them (`## ## What's next`). Fixed.
- **22 section `_index.md` pages have no body** (front matter only), so they produce no chunks. They are still loaded (511 pages).
- **chunk_id** = sha256(doc_id, chunker, position, content)[:16] as in the guide. Position is in the hash, so inserting a chunk earlier in a doc changes the ids of later chunks (stable only for unchanged chunk sequences).
- **Embedding cache key (Phase 2, decided now)**: `sha256(embed_model + dims + exact_embedded_text)`, jsonl, not keyed by `chunk_id`. Deviation from "chunk hash + model": changing the heading-path prefix format, chunk size or model changes the text/model and so the key; unchanged text keeps its vector even if its position moved, and identical text shared by both chunkers is embedded once.
- **Tiny-chunk rule (final, owner decision 2026-10-24): no minimum-token rule; "What's next" sections are stripped in the loader.** `ingest.loaders.strip_whats_next` removes every `## What's next` section (heading to the next heading of the same or higher level, fence-aware) from the cleaned text *before* either chunker runs, so fixed and heading see identical text. Reason: those sections are navigation links to other pages, not answer content, and they made up many of the tiny chunks (and were being retrieved as irrelevant hits, e.g. "Safely Drain a Node > What's next" at dense rank 1). Effect (`eval/results/phase1_stats.txt`): 281 sections / 30,606 tokens removed (all exactly `## What's next`: 279 from `{{% heading "whatsnext" %}}`, 2 literal); fixed chunks 4,211 -> 4,103, heading chunks 4,824 -> 4,544; heading chunks under 100 tokens 568 (11.8%) -> about 415 (9.1%), fixed 131 (3.1%) -> 132 (3.2%) (these two figures are from the 4,545-chunk run, before the indentation fix below; the final run is in `phase1_stats.txt`); max tokens unchanged (649 heading, 408 fixed), 0 over 800; the same 22 body-less `_index` pages. The remaining short chunks are real short sections and are kept. Answers generated before this change are in `eval/results/generation_log.jsonl`; their chunk text is frozen in `eval/results/context_snapshot.json` because chunk ids change on re-indexing.
- **Why 281 and not 333/469.** The shortcode scan counted all `heading` shortcodes: 469 uses on 333 pages = `whatsnext` 279 (279 pages) + `prerequisites` 171 + `cleanup` 8 + `objectives` 7 + `seealso` 4 (2 pages). Only `whatsnext` is stripped. 279 shortcode uses + 2 literal `## What's next` headings = 281. The first implementation removed 280: one page (`tasks/administer-cluster/kubeadm/upgrading-windows-nodes`) has the heading indented by one space, which CommonMark allows (0-3 spaces); the loader regexes now accept it (test added). After the fix no `What's next` heading remains in either chunk file; the two "What's next" strings still in chunk text are prose mentions. `See also` (4 uses, 2 pages) was not asked for and is left in.
- **Headless include partials are excluded (owner decision, done 2026-10-24).** 9 of the 511 pages sat under `tasks/tools/included/` and are Hugo headless partials (`headless: true`, `_build.render: never`), e.g. `kubectl-whats-next` (title "What's next?"). ## Phase 2
- **Effective `index_options` is `bbq_hnsw`** (m=16, ef_construction=100, rescore_vector oversample 3.0) although the mapping did not set it: ES 9.5.5 quantises `dense_vector` to binary by default for dims >= 384. The saved `eval/results/mapping.json` shows it (field mapping with `include_defaults`). Phase 3/7 can compare against explicit `hnsw` / `int8_hnsw` if dense recall looks low.
- **Mapping additions** to the guide's mapping: `token_count` and `position` (integer), plus 1 shard / 0 replicas so the single node stays green.
- **Actual embedding usage matched the estimate exactly**: 2,750,672 tokens, 91 calls, $0.0550 (`eval/results/embed_run.json`). 9,035 chunks across the two chunkers share 9,009 unique texts (26 identical texts embedded once).
- **Cache size**: `data/embed_cache/text-embedding-3-small.jsonl` is 273 MB (9,009 vectors as JSON text), bigger than the guide's "well under 200 MB" because jsonl stores floats as text. ES stores the index in 128 MB. Parquet or float16 would shrink it; not worth it for a laptop project.
- **Spend guard is per run**, not cumulative across runs; re-runs cost nothing because of the cache.
- **Re-running the indexer** re-sends all 9,035 docs to ES (same `_id`, so idempotent) but makes zero embedding calls.

## Phase 3 + 4
- **Effective kNN rescore behaviour (measured, `index_options` untouched).** The index is `bbq_hnsw` with `rescore_vector.oversample=3.0`. A kNN search with no rescore parameter returned exactly the same scores and order as one passing `rescore_vector: {oversample: 3.0}`, so the index-level default is applied at query time. Returned scores sit within 7.5e-5 (mean 5e-5) of the exact float cosine `(1+cos)/2` computed from the cached vectors, and that gap did not shrink with `oversample: 10`, so it is not leftover quantisation error; I do not know its exact cause (float32 storage / normalisation are candidates). Neighbouring hits differ by ~1e-3 or more, so ranks are unaffected in the cases checked. These measurements were taken at k=50, num_candidates=200; Phase 4b below raised the retriever window to k=200, num_candidates=800. Re-run at k=200 (the current default): default scores equal those with explicit `oversample` 3 and 10, max gap to exact cosine 7.48e-05, mean 5.05e-05 (5.16e-05 at k=50), so the conclusion holds.
- **Query embeddings use the ingestion cache file** (`data/embed_cache/<model>.jsonl`, key = sha256(model + dims + exact text)) and the same `SpendGuard`. The 273 MB file is not loaded into memory per process: a miss in the small in-process dict streams the file for the key; new queries are appended. Each uncached query asks for confirmation first.
- **BM25 title boost duplicates doc-level matches.** `title^2` and `heading_path^1.5` are copied onto every chunk of a page, so when a query matches the title, all chunks of that page score identically (e.g. four "Safely Drain a Node" chunks at 15.4053) and fill the top-k. Seen with both chunkers, worst with `fixed` (title-only heading_path on every chunk). Eval collapses to distinct `doc_id`s, so this does not inflate recall, but it fills result lists.
- **RRF** (`rag.retrieve.rrf`): k=60, rank from 1, sums as exact fractions, a repeated id in one list counts once at its best rank, ties keep first-seen order. Each hybrid hit carries `ranks` per input list.
- **CLI gotcha**: a query that looks like a flag needs `--query=--max-requests-inflight`.
- **Mistake in my first demo query.** I claimed the conceptual query avoided the target page's key terms, using a regex I had double-escaped (every count came out 0). BM25's `explain` showed the page does contain "fork" and "bomb". That query was discarded and replaced by one verified against document frequency (it shares `machine` (12% of pages), `start` (46%) and `new` (45%); with a 20% cutoff only `machine` counts as distinctive, versus `fork`, `bomb`, `protect` for the discarded one). That check now lives in `eval/overlap.py` with tests, including a non-zero regression case.

## Phase 4b: retriever window (distinct-doc shortfall)
- **Problem**: with the original 50-chunk window, `eval/results/pool_check.txt` (100 proxy queries: page titles + leaf headings, seed 0; not the golden set) shows queries with fewer than 10 distinct docs: fixed bm25 29, dense 13, hybrid 6; heading bm25 30, dense 6, hybrid 1. A recall@10 over distinct docs would have been capped by list length, and more so for `fixed` (many chunks per page).
- **Fix chosen: raise the per-retriever window to 200** (`POOL=200`, kNN `k=200`, `num_candidates=800`, keeping the original 4:1 ratio) rather than capping chunks per doc before fusion. At 200: dense 0 and hybrid 0 short queries on both chunkers (min 31/35 distinct docs for fixed, 36/47 for heading). A pre-fusion per-doc cap would change which chunks compete in RRF and hide agreement between chunks of one page; a deeper window only adds candidates.
- **Remaining BM25 shortfalls are not a window problem**: 7 queries per chunker still give <10 distinct docs, all rare CamelCase identifiers (`PodReference`, `ResourceSpec`, ...) that match only 1-14 chunks in the whole index (checked: chunk_hits << 200). That is exact-term retrieval working as it should; Phase 7 should report such queries as "list exhausted", not as a miss caused by the window.
- **Side effect that matters (my earlier claim was wrong)**: the window is not a pure recall guard. The kNN result depends on `k`/`num_candidates` under `bbq_hnsw`: against exact brute-force cosine (`eval/results/knn_recall_check.txt`, 40 proxy queries) `k=50,nc=200` agrees on 0.992 of the top-10 and 0.978 of the top-50, `k=200,nc=800` on 1.000 and 0.999. The old setting had missed a rank-9 hit for the pid-limiting query; with the near-exact kNN, hybrid/heading puts a 37-token "Stop the Docker daemon" chunk first (BM25 rank 2 + dense rank 9) and pid-limiting second. The earlier "hybrid ranks it 1st" demo result was partly an ANN artefact. RRF mass from deep ranks (1/(60+r)) can also reorder results, so `pool` stays a parameter of `hybrid()` and Phase 7 should sweep it (50/100/200) on the golden set before the README states a hybrid result.
- `rag.retrieve.distinct_docs()` collapses a ranked chunk list to one hit per doc (first = best chunk); eval must compute recall@k/MRR on that list.

## Phase 5: generation
- **Model/prices (looked up 2026-10-23)**: `claude-sonnet-5-5`, $2 / $10 per 1M input/output tokens (platform.claude.com pricing + models overview), 1M context at standard pricing. `ANSWER_MODEL` in `.env.example` already holds it. `PRICES` in `rag/generate.py` refuses unknown models.
- **Structured output** via `output_config.format` json_schema `{answerable, sentences:[{sentence, citations}]}`. `answerable` is an addition to the guide's `[{sentence, citations}]` so a refusal is machine-checkable. `validate_answer` rejects citation numbers outside 1..n, uncited facts, refusals that cite, non-int/bool citations, bad shapes; an invalid answer is raised as `InvalidAnswer` but still billed and logged (`error` field).
- **Sonnet 5.5 specifics**: adaptive thinking cannot be disabled (400) and forced `tool_choice` is rejected, so structured output is the JSON route; `effort` is set explicitly to `medium` (the model default is `high`); no sampling parameters are sent. Thinking tokens are part of `usage.output_tokens`, which is what the cost uses. `MAX_TOKENS=4000` is the ceiling and the worst case charged to the spend guard before the call; the guard is then settled to the real usage cost.
- **Estimates**: input tokens estimated as chars / 2.5 (docs: ~2.5M characters per 1M tokens); on the three test questions the estimate was within -2% to +8% of the reported input tokens.
- **Context**: hybrid on the heading chunker, 40 fused candidates, then max 8 chunks with at most 2 per doc (context cap only).
- **Exhausted-list rule (implemented in `eval/metrics.py`).** A retriever list is exhausted when it returns fewer chunks than the window. Such queries stay in recall/MRR as ordinary queries (expected doc not returned = miss, 0), never dropped from the denominator; `aggregate()` reports `exhausted`, `exhausted_share`, `exhausted_missed` (exhausted and the expected doc not returned) and `short` (<10 distinct docs, any cause) separately. Unanswerable questions have no expected docs and raise if passed to `evaluate_query`.
- **Generation logs now carry chunk text** (`content` per chunk) so an answer can be verified without the index. The three pre-change answers use `eval/results/context_snapshot.json` instead.

- **Price sources (both fetched 2026-10-23/24, per 1M tokens, standard non-batch)**: models overview `https://platform.claude.com/docs/en/about-claude/models/overview` (IDs `claude-sonnet-5-5`, `claude-haiku-5-5`) and pricing `https://platform.claude.com/docs/en/about-claude/pricing`. OpenAI embeddings: `https://developers.openai.com/api/docs/pricing` (and the model page `.../models/text-embedding-3-small`): text-embedding-3-small $0.02 per 1M tokens (no batch price listed).
- **Model/price (looked up 2026-10-24)**: `claude-haiku-5-5` (platform.claude.com models overview), $0.10 / $0.50 per 1M input/output tokens for prompts up to 100K tokens ($0.50 / $2.50 above), from the pricing page. `VERIFIER_MODEL` in `.env.example`. `effort` is set to `low`; no sampling parameters; structured output via `output_config.format`.
- **One batched call per answer**: every (sentence, cited chunk) pair gets `yes` / `partial` / `no` and a one-line reason; only cited excerpts are sent. The verifier is told to judge only against the excerpt text, not its own knowledge. `validate_verdicts` requires exactly one well-formed judgement per expected pair (no missing, extra or duplicate pairs, enum verdicts, non-empty reason). Bad output raises `InvalidVerdicts` but the tokens are still billed and counted.
- **Definitions**: citation precision = share of citations judged `yes` (the guide's definition). A sentence is *unsupported* when none of its citations is `yes` or `partial`, *partially supported* when its best verdict is `partial`. A refusal has no citations, so nothing is verified.
- **Mutation test** (`eval/verify_mutation.py`): 10 deliberately wrong pairs from the saved answers, 5 with the citation swapped to an unrelated excerpt and 5 with a changed number / wrong component / inverted claim. Expected verdict `no`; `partial` is a soft catch, `yes` a miss. Five controls were added (C01 a saved model sentence; C02-C05 sentences I authored, each verbatim from the cited excerpt, checked by a test) and shuffled in with the wrong pairs.
- **Results (2026-10-24, `claude-haiku-5-5`, effort low; `eval/results/verify_mutation.json`, `verification_log.jsonl`)**
  - *Mutation test*: wrong pairs 10: **7 `no`, 3 `partial`, 0 `yes` (missed)**. Swapped citations: 5/5 `no`. Altered sentences: 2 `no` (M09 multiplied vs summed, M10 inverted exemption) and 3 `partial` (M06 changed number 262144 -> 524288, M07 kubelet -> kube-scheduler, M08 inverted "does not ensure"). Controls 5: **5 `yes`, 0 false alarms**. Caveats: n=10 and n=5; the controls are verbatim sentences, the easiest case for a verifier. The three `partial`s on altered sentences have reasons that say "contradicted" / "unsupported", which by the rubric should be `no`, so `partial` is a loose bucket.
  - *Saved answers* (rows 0 and 1, no regeneration): citation precision (share `yes`) 4/7 = 0.57 and 3/5 = 0.60; no `no` verdicts, so no "unsupported" sentences; 5 sentences `partial`. By my own reading at least 3 of those 5 are false alarms: the pid-limiting "fewer than 250 Pods" sentence is word-for-word what the page says ("less than 250 Pods"), and the verifier's own reason for it says "consistent". So the precision figure understates, and `yes` vs not-`yes` is a noisy signal in the paraphrase case. ### Verifier rubric v2 (`claims-v2`, 2026-10-24)
- **Why**: v1 asked the model for a yes / partial / no verdict directly and `partial` turned out to be a loose bucket (faithful paraphrases marked partial; sentences whose own reason said "contradicted" marked partial).
- **Change (output format, same model, same effort)**: for each (sentence, cited chunk) pair the model lists the sentence's atomic claims and classifies each as `supported` / `unsupported` / `contradicted` (paraphrase, synonyms and equivalent numbers/formats count as supported), plus a one-line reason. The model is no longer allowed to return a verdict (an extra `verdict` key is rejected). **The verdict is derived in code (`rag.verify.derive_verdict`)**: any `contradicted` -> `no`; else all `supported` -> `yes`; else some `supported` (none contradicted) -> `partial`; else (none supported) -> `no`. Unit-tested for every branch. `MAX_TOKENS` raised 3000 -> 6000 because claim lists are longer. Log rows carry `rubric: "claims-v2"`; older rows (no field) are v1.
- **The mutation set is a DEV SET, not an accuracy measurement.** v2 was written after seeing v1's failures on that same set, so its scores below are optimistic by construction. The verifier's accuracy will come from the owner's hand labels at checkpoint 4. No rubric tuning was needed after the first v2 run (one run per model, no iteration).
- **Set (25 pairs)**: the 10 wrong pairs and 5 verbatim controls from v1, plus 10 paraphrased controls (P01-P10) that I wrote from the cited excerpts (meaning kept, wording changed, numbers in equivalent form such as 262,144 / 1,000 / 32,768). The paraphrases are reviewed by eye only; a test checks they are not verbatim copies.
- **Haiku 5.5 results** (`verify_mutation_haiku.json`; v1 results are kept in `verify_mutation_v1.json`): wrong pairs **10/10 `no`** (v1: 7 `no`, 3 `partial`); verbatim controls **5/5 `yes`**, false-alarm rate 0/5; paraphrased controls **10/10 `yes`**, false-alarm rate 0/10. Cost $0.0023.
- **Sonnet 5.5 cross-check** (`verify_mutation_sonnet.json`, same set, same rubric, one run): identical verdicts on **25/25** pairs (wrong 10/10, verbatim 5/5, paraphrased 10/10). The claim lists agree exactly on 16/25 pairs; on the other 9 Haiku splits the sentence into more claims (e.g. `sss` vs `s`) but the derived verdict is the same. Cost $0.0405 (about 17x Haiku), so Haiku stays the verifier.
- **Saved answers re-verified under v2** (rows 0 and 1, `verification_log.jsonl`): citation precision 6/7 = 0.86 and 5/5 = 1.00 (v1: 0.57 and 0.60); no `no` verdicts. The pid-limiting sentence citing [4] is still `yes`. One `partial` remains: row 0 sentence 5 ("reserve an amount of PIDs for node overhead ... so that host daemons such as the kubelet are protected"); the excerpt says PIDs can be reserved for the OS and daemons and, separately, that the aim is to stop Pods starving daemons such as the kubelet, but never links the reservation to the kubelet in one statement. That is a defensible synthesis-vs-support call and a good candidate for the hand-labelling sample. These two precision numbers are from 12 pairs and are not the system's faithfulness.
- **Limits to keep in mind**: 25 hand-built pairs; wrong pairs are blatant (unrelated excerpt, changed number, inverted claim), not subtle half-truths; the controls are simple one-claim sentences; Sonnet agreeing with Haiku shows consistency, not correctness.

## Phase 7a: golden-set tooling (2026-10-24)
- **Files**: `eval/doc_ids.tsv` (the 502 indexed pages with URL, title and chunk counts; `python -m eval.docids --write` regenerates it), `eval/docids.py` (URL / title / id lookups; a section URL maps to `<path>/_index`), `eval/term_stats.py` (chunks and docs containing a term, per chunker; literal substring on cleaned chunk text, not BM25 tokens), `eval/golden_check.py` (format + known-doc_id + 1-3-expected-docs + counts-vs-plan validator), `eval/golden_template.jsonl`, `eval/GOLDEN_README.md`. The owner writes `exact_term` (10) and `unanswerable` (5) questions into `eval/golden_owner.jsonl`.
- **`eval.draft_questions`** drafts `conceptual` (22) and `mixed` (16) candidates (slightly above the planned 20 / 15 so weak ones can be cut) with `ANSWER_MODEL`, one call per sampled chunk, one chunk per page, seeded (`SEED=7`), spread over concepts 8+5 / tasks 9+5 / reference 5+6. Eligible chunks: heading chunker, 150-600 tokens, under 35% fenced code and under 40% table rows, no raw HTML entity; mixed also needs a backticked exact term (flag, camelCase name, snake_case, hyphenated name). Conceptual sampling excludes `reference/config-api/` and `reference/instrumentation/metrics` (generated field / metric listings make poor conceptual material; they stay eligible for mixed).
- **Paraphrase controls in the prompt**: conceptual drafts must avoid the passage's flag / field / command names and title words and never copy 3+ consecutive words; mixed drafts must contain exactly one verbatim exact term (validated in code: literally in the passage and in the question) and otherwise paraphrase. Drafting is structured output validated in code; invalid drafts are recorded as errors, still billed, and shown in the review table.
- **Flagging** (never silent dropping): `overlap_ratio` against the whole source page at or above 0.5 (conceptual) / 0.6 (mixed), 2 or more corpus-rare shared terms (document frequency under 20%), or a copied 4-word run. For mixed drafts the declared exact term's own words are removed before measuring. Thresholds come from the pid-limiting calibration (flawed query 0.67 / 3 distinctive terms, replacement 0.38 / 1) and are not tuned further.
- **No retrieval output is shown with the drafts**, so expected docs cannot be anchored on what a retriever returns; `source_doc_id` is only a suggestion (the model saw one passage and cannot know a second page also answers).
- **Cost** (dry run, Sonnet 5.5, effort low): 38 drafts, about 34k input tokens, typical $0.22 (assumes ~400 output tokens per draft; that figure is an assumption, the real cost is read from usage), worst case $0.64 (every call at the 1,500-token ceiling).
- **Gap found: raw HTML entities in chunk text.** 177 fixed and 160 heading chunks (3.5-4.3%, 38 docs, mostly the generated `reference/config-api/*` pages) contain `&quot;` (about 1,080 times), `&#34;`, `&lt;`, `&gt;`, `&amp;`, `&#x2713;`. The loader strips layout tags but never decodes entities, so BM25 sees tokens like `quot` and the embedded text is noisier.
